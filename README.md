# GEMBA SAFETY

เว็บแอปเดินตรวจ **ความปลอดภัย** ในโรงงาน — พบปัญหาแล้วส่งให้ผู้จัดการและหัวหน้างานเข้าแก้ไข
แนบรูปหลังแก้กลับมาเป็นหลักฐาน แล้วผู้ตรวจกดปิดงาน

**เว็บใช้งานจริง: <https://topmaha.github.io/Gemba-Safety/>** · API: <https://gemba-safety-api.wiphawas-sketchup.workers.dev>

ต่อยอดจาก Gemba Walk (<https://gemba-audit.pages.dev>) โดยเปลี่ยนโจทย์จาก "เดินตรวจทั่วไป"
เป็น "งานความปลอดภัยโดยเฉพาะ" และเพิ่มสองเรื่องที่ของเดิมไม่มี

1. **ข้อมูลชุดเดียวกันทั้งโรงงาน** — ทุกคนเห็นใบแจ้งปัญหาใบเดียวกัน สถานะเดียวกัน
   ผ่าน Cloudflare Worker + D1 (ไม่ใช่ข้อมูลแยกเครื่องใครเครื่องมัน)
2. **สิทธิ์ผู้เข้าใช้งาน (RBAC)** — ฐานข้อมูลบทบาท/สิทธิ์ถูกสร้างและใส่ค่าตั้งต้นไว้แล้ว
   ส่วนทะเบียน "ใครเป็นบทบาทไหน" ตั้งใจเว้นว่างไว้ ค่อยกรอกทีหลังที่หน้า `/admin/roles`

ออกแบบให้ใช้บนมือถือหน้างานเป็นหลัก ใช้ได้แม้สัญญาณไม่ถึง และรองรับสองภาษา ไทย/อังกฤษ

## 1. วงจรงานของระบบ

```text
เดินตรวจตามเช็คลิสต์
        │  ข้อไหน "ไม่ผ่าน" → เปิดใบแจ้งปัญหาอัตโนมัติ (พร้อมรูปและระดับความรุนแรง)
        ▼
   ใบแจ้งปัญหา  ── มอบหมาย ──▶  ผู้จัดการ + หัวหน้างาน
   (รอมอบหมาย)                        │  กดรับงาน → ลงมือแก้
        ▲                              ▼
        │                        บันทึกการแก้ไข + แนบรูปหลังแก้  (บังคับ)
        │ ตีกลับ (พร้อมเหตุผล)         │
        └──────── ตรวจรับไม่ผ่าน ◀──── รอตรวจรับ ──── ตรวจรับผ่าน ──▶ ปิดงาน
```

| สถานะ | ความหมาย | ใครทำต่อ |
|---|---|---|
| `open` รอมอบหมาย | เปิดใบแล้วแต่ยังไม่มีผู้รับผิดชอบ | ผู้มีสิทธิ์ `finding.assign` |
| `assigned` มอบหมายแล้ว | ส่งให้ผู้จัดการ/หัวหน้างานแล้ว | ผู้รับผิดชอบกด "รับงาน" |
| `in_progress` กำลังแก้ไข | รับงานแล้ว อยู่ระหว่างแก้ | ผู้รับผิดชอบ |
| `fixed` รอตรวจรับ | แก้เสร็จ แนบรูปหลังแก้แล้ว | ผู้แจ้ง หรือผู้มีสิทธิ์ `finding.verify` |
| `closed` ปิดงาน | ตรวจรับผ่าน | — |
| `cancelled` ยกเลิก | ไม่ใช่ปัญหาจริง/ซ้ำใบอื่น (ต้องระบุเหตุผล) | — |

**วันครบกำหนดแก้ไขคิดจากระดับความรุนแรงอัตโนมัติ** (แก้ค่าได้ที่ `/admin/roles`)

| ความรุนแรง | ให้เวลาแก้ (ค่าตั้งต้น) |
|---|---|
| วิกฤต (critical) | 1 วัน |
| สูง (high) | 3 วัน |
| ปานกลาง (medium) | 14 วัน |
| เบา (low) | 30 วัน |

## 3. ข้อมูลที่ทุกคนเห็นตรงกัน

หัวใจของข้อกำหนดข้อแรก: **ทุกเครื่องอ่านและเขียนข้อมูลชุดเดียวกัน**

```text
หน้าจอ  →  hooks/useData.ts  →  lib/api.ts  →  lib/db.ts (สำเนาในเครื่อง)
                                     ↓
                              lib/queue.ts (คิวใน IndexedDB)
                                     ↓
                              lib/sync.ts  ⇄  lib/net.ts  →  Worker → D1 / R2
```

- กดบันทึกแล้ว **เขียนลงเครื่องทันที ไม่รอเน็ต** งานเข้าคิวรอส่ง
- ตัวซิงก์ส่งของค้างขึ้นก่อน แล้วดึงของใหม่ลงมาทับสำเนาในเครื่อง
- **ดึงของใหม่ทุก 1 นาทีตราบใดที่เปิดแท็บอยู่** ใบที่คนอื่นเพิ่งปิดจึงหายจากจอเราเอง
  (เดิมดึงเฉพาะตอนเปิดแอปหรือมีของค้าง)
- ของที่ยังไม่ถูกส่งขึ้นเซิร์ฟเวอร์จะไม่ถูกข้อมูลจากเซิร์ฟเวอร์ลบทิ้ง — ดู `keepPending()` ใน `src/lib/sync.ts`
- ป้ายสถานะบนหัวจอบอกตลอดว่า ซิงก์แล้ว / ยังไม่ซิงก์ (กี่รายการ) / ออฟไลน์ กดเพื่อลองใหม่ได้

> ⚠️ **ถ้าไม่ตั้ง `VITE_API_URL` แอปจะทำงานโหมดในเครื่อง** ข้อมูลจะอยู่แค่เครื่องคนเดียว
> ไม่ถูกแชร์กับใคร เหมาะกับการพัฒนา UI เท่านั้น — วิธีตั้งค่าอยู่ใน [README-SETUP.md](README-SETUP.md)

## 4. สิทธิ์ผู้เข้าใช้งาน

โครงมาตรฐาน 4 ตาราง: `permissions` → `roles` → `role_permissions` → `user_roles`

| บทบาท | ทำอะไรได้ |
|---|---|
| `admin` ผู้ดูแลระบบ | ทุกสิทธิ์ (17 รายการ) |
| `safety` เจ้าหน้าที่ความปลอดภัย (จป.) | ตรวจ · มอบหมาย · ตรวจรับปิดงาน · เห็นทุกพื้นที่ · จัดการข้อมูลหลัก |
| `manager` ผู้จัดการ | รับงาน · มอบหมายต่อ · แก้ไข · เห็นใบแจ้งทุกพื้นที่ · ดูรายงาน |
| `supervisor` หัวหน้างาน | รับงาน · ลงมือแก้ · แนบรูปหลังแก้ |
| `inspector` ผู้เดินตรวจ (บทบาทตั้งต้น) | วางแผน · เดินตรวจ · เปิดใบแจ้ง |
| `viewer` ผู้ดูอย่างเดียว | ดูแดชบอร์ดและรายงาน |

**ตาราง `user_roles` เริ่มต้นว่างเปล่าโดยตั้งใจ** ระหว่างที่ยังไม่ได้กรอก ทุกคนที่ล็อกอินได้
จะได้บทบาทตั้งต้นตาม `app_settings.default_role_code` (ตั้งต้นคือ `inspector`)
เมื่อกรอกทะเบียนสิทธิ์ครบแล้วให้เปลี่ยนค่านี้เป็น `viewer` ระบบจะกลายเป็น "ปิดโดยปริยาย" ทันที

กรอกได้ที่ **`/admin/roles`** (ต้องเข้าโหมดผู้ดูแลก่อน) — เลือกคน เลือกบทบาท เลือกขอบเขตพื้นที่
(`ทั้งโรงงาน` หรือเฉพาะพื้นที่) · คนหนึ่งถือได้หลายบทบาท สิทธิ์ที่ได้คือผลรวมของทุกบทบาท

**สองกติกาที่ผูกกับตัวบุคคล ไม่ต้องเปิดสิทธิ์เพิ่ม**

1. ผู้ที่ถูกมอบหมาย (ผู้จัดการ/หัวหน้างาน) รับงานและรายงานผลใบของตัวเองได้เสมอ
2. ผู้แจ้งตรวจรับใบที่ตัวเองแจ้งได้ เพราะเป็นคนที่รู้ว่าปัญหาหายจริงหรือยัง

> ⚠️ **สิ่งที่ฝั่งหน้าเว็บทำคือ "ซ่อนปุ่ม" ไม่ใช่ด่านกัน** ด่านจริงอยู่ที่ Worker
> งานที่แก้กติกาของระบบ (ทะเบียนผู้ใช้ · สิทธิ์ · พื้นที่ · หมวด · เช็คลิสต์ · ตั้งค่า)
> ต้องมีเซสชันผู้ดูแลที่เซิร์ฟเวอร์ออกให้เท่านั้น ส่วนใบแจ้งปัญหา Worker บังคับลำดับสถานะให้
> (เช่น ตรวจรับได้เฉพาะใบที่แก้เสร็จแล้ว · เปลี่ยนเป็น "แก้เสร็จ" ต้องมีรูปหลังแก้)

## 5. เช็คลิสต์ความปลอดภัย

หมวดตรวจ 12 หมวด × ข้อตรวจ 48 ข้อ — **Super Admin เพิ่ม/แก้/ปิดข้อตรวจได้เองที่ `/admin/settings` → แท็บ "เช็คลิสต์"**
(ระบบเสนอรหัสข้อถัดไปให้อัตโนมัติ เช่น PPE-04 → PPE-05 · ไม่มีปุ่มลบโดยตั้งใจ ให้ "ปิดใช้งาน" แทนเพื่อเก็บผลตรวจเดิม)
เพิ่มหรือแก้ชื่อหมวดได้ที่แท็บ "หัวข้อการเดิน"

| # | หมวด | # | หมวด |
|---|---|---|---|
| 01 | อุปกรณ์ป้องกันส่วนบุคคล (PPE) | 07 | การล็อกและแขวนป้าย (LOTO) |
| 02 | การ์ดเครื่องจักรและจุดหนีบ | 08 | ที่สูงและที่อับอากาศ |
| 03 | ระบบไฟฟ้า | 09 | 5ส และความเป็นระเบียบ |
| 04 | สารเคมีและ SDS | 10 | การยศาสตร์และการยกเคลื่อนย้าย |
| 05 | อัคคีภัยและทางหนีไฟ | 11 | พฤติกรรมความปลอดภัย (BBS) |
| 06 | รถยก/MHE และการจราจร | 12 | สิ่งแวดล้อมและของเสีย |

ตอนบันทึกการเดิน ระบบดึงข้อตรวจของ **หมวดที่เลือกไว้เท่านั้น** มาให้ติ๊ก ผ่าน / ไม่ผ่าน / ไม่เกี่ยว
(แตะปุ่มเดิมซ้ำเพื่อล้างคำตอบ · ปุ่ม "ข้อที่เหลือผ่านทั้งหมด" ต่อหมวดช่วยให้เดินเร็วขึ้น)
ข้อที่ติ๊ก "ไม่ผ่าน" จะเปิดช่อง **บันทึกปัญหาที่พบ** ทันที — รายละเอียดปัญหา · ความรุนแรง · การแก้ไขเบื้องต้นหน้างาน · รูปถ่าย (สูงสุด 5 รูป)
แล้วกลายเป็นใบแจ้งปัญหาหนึ่งใบต่อหนึ่งข้อ ความรุนแรงตั้งต้นมาจากข้อนั้น (เช่น การ์ดเครื่องจักรหลุด = วิกฤต) แต่ผู้ตรวจปรับได้
ผลตรวจรายข้อดูย้อนหลังได้ที่หน้าประวัติ → รายละเอียดการเดิน (ข้อไม่ผ่านโยงไปใบแจ้งพร้อมรูป)

## 8. ตารางที่เพิ่มในฐานข้อมูล

| ตาราง | หน้าที่ |
|---|---|
| `safety_findings` | ใบแจ้งปัญหา — หัวใจของระบบ (สถานะ · ความรุนแรง · ผู้รับผิดชอบ · วันครบกำหนด) |
| `finding_photos` | รูปประกอบ แยก `phase` เป็น `before` / `after` |
| `finding_events` | ไทม์ไลน์ทุกการเปลี่ยนมือและทุกความเห็น |
| `notifications` | กล่องงานของผู้รับผิดชอบ (แสดงที่กระดิ่งและหน้า "งานของฉัน") |
| `safety_checklist_items` | แม่แบบข้อตรวจ ผูกกับหมวดใน `walk_themes` |
| `walk_checklist_results` | ผลตรวจรายข้อของการเดินแต่ละครั้ง + ใบแจ้งที่เกิดจากข้อนั้น |
| `roles` · `permissions` · `role_permissions` · `user_roles` | สิทธิ์ผู้ใช้งาน |

**พฤติกรรมตอนลบ** — ใบแจ้งเป็นหลักฐาน จึงใช้ `RESTRICT` กับผู้แจ้ง/ผู้รับผิดชอบ/พื้นที่
(ลบคนที่มีใบผูกอยู่ไม่ได้ ให้ปิด `is_active` แทน) ส่วนรูป/ไทม์ไลน์/แจ้งเตือนใช้ `CASCADE`
และผลตรวจใช้ `RESTRICT` กับข้อตรวจ — ให้ปิด `is_active` แทนการลบเสมอ

## 9. ข้อควรรู้

- **โซนเวลา** Asia/Bangkok ทั้งหมด สัปดาห์เริ่มวันอาทิตย์ ห้ามใช้ `new Date()` ตรง ๆ ในหน้าจอ
  ให้เรียกผ่าน `src/lib/time.ts` เสมอ (ฝั่ง Worker ใช้ `date('now', '+7 hours')`)
- **รูปภาพ** ย่อด้านยาวไม่เกิน 1400px แปลงเป็น JPEG ก่อนเก็บ · ตอนออฟไลน์เก็บใน IndexedDB
  เป็นคีย์ `local:…` แล้วตัวซิงก์อัปโหลดขึ้น R2 ให้เอง
- **รูปหลังแก้เป็นหลักฐานบังคับ** ปิดได้ที่ `/admin/roles` ถ้าบางงานถ่ายรูปไม่ได้จริง ๆ
- **`src/lib/safetySeed.ts` ต้องตรงกับ `worker/seed-safety.sql` เสมอ** (id เดียวกันทุกแถว)
  ไม่งั้นเครื่องที่ยังไม่ได้ซิงก์จะอ้าง `item_id` ที่เซิร์ฟเวอร์ไม่รู้จัก
- **ปิดบัญชีมีผลทันที** ผู้ดูแลปิด `is_active` หรือถอน `can_login` แล้วผู้ใช้จะถูกเด้งออกในรอบซิงก์ถัดไป
- **ล้างข้อมูล** `/admin/settings` → แท็บ "ระบบ" (ล้างสำเนาในเครื่องเท่านั้น ไม่กระทบเซิร์ฟเวอร์)
